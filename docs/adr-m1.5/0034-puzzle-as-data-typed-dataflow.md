# ADR-0034: Puzzle as a first-class typed dataflow document

- **Status:** Accepted
- **Date:** 2026-10-26
- **Deciders:** Snorre
- **Related:** ADR-0006, ADR-0009, ADR-0010, ADR-0011, ADR-0023, ADR-0039

## Context

M1 checks understanding through quiz-style concept gates. That is a valid
assessment tool, but it is not a spatial puzzle: the player reads a prompt and
submits an answer. The learning design needs puzzles that are solved by moving
through and manipulating the world. It also needs a reusable authoring
contract, not a one-off Signal Ferry implementation.

Three constraints shape the decision:

- Pack content must stay declarative. Arbitrary scripts in a pack violate
  ADR-0010.
- The puzzle graph must be testable without Matter.js, Phaser, a browser, or
  rendered content.
- A second puzzle type must be authorable without engine code. Otherwise the
  foundation is unproven.

## Decision

A puzzle is a **first-class data object** loaded with its level package. The
document is a typed dataflow graph, not a script and not a per-puzzle class.

### Document

A puzzle document contains:

- identity: `schemaVersion`, `id`, `title`, `objectiveIds`, `conceptIds`;
- activation: `roomStart | zoneEnter | interact`;
- `tether` policy (`normal | stretch | off`);
- `nodes`: the ten primitive types below;
- `links`: typed edges between nodes;
- `win`: a fixed predicate expression;
- `reset`: which props and nodes return to their initial state;
- `evidence`: solve event and diagnostic counters;
- `rewards`: ability, flag, and map-node unlocks;
- `solution`: a serialised action trace used by tests and reachability
  validation;
- `hints`: authored text, never generated by engine code.

### Primitive vocabulary

| Node | State | Purpose |
|---|---|---|
| `prop` | free / carried / placed / docked | A physical object the puzzle can reference |
| `receptor` | idle / occupied / bound | Accepts a prop by tag and shape |
| `pulseSource` | idle / cooldown / travelling | Ability-triggered wave sender |
| `plate` | released / pressed | AABB pressure sensor |
| `relay` | inactive / active | Boolean combination of inputs |
| `gate` | closed / open | Logical output |
| `timer` | idle / running / elapsed | Deterministic tick countdown |
| `counter` | count | Deterministic increment/reset |
| `zone` | empty / occupied | AABB presence sensor |
| `trigger` | idle / fired | One-shot or repeatable event source |

### Typed links

Links are a closed vocabulary: `pulse`, `bind`, `press`, `release`, `enter`,
`exit`, `increment`, `start`, `stop`, `reset`, `elapsed`, `reached`,
`activate`, `deactivate`, `open`, `close`.

A link is valid only when its source and target node types permit it. The
validator rejects unknown types, unknown endpoints, duplicate IDs, illegal
pairs, and boolean relay cycles.

### Evaluation

Evaluation is a **pure runtime** in `src/puzzle`:

- input is an immutable world snapshot containing player and prop AABBs, prop
  states, and the current tick;
- zones and plates are AABB checks over that snapshot;
- timers, counters, pulses, and links advance on fixed ticks;
- output is a new serialisable run state plus semantic events;
- the module never imports Matter.js, Phaser, DOM, or pack-loading code.

The world owns bodies, collisions, hazards, and rendering. The puzzle runtime
owns graph state, win conditions, reset, rewards, and evidence counters.

### Win and reset

Win conditions are fixed predicates: `gateOpen`, `receptorBound`,
`platePressed`, `relayActive`, `timerElapsed`, `counterReached`,
`zoneOccupied`, `propState`, `flagSet`, and `allOf` / `anyOf` / `not`.

Reset returns referenced props to spawn, removes carry constraints, clears
sensor and relay state, resets timers and counters, closes unsolved gates, and
preserves evidence counters. A solved puzzle stays latched until an explicit
new run.

### Solution trace

The solution trace is data, not a recording. It names actions (`move`,
`pickup`, `drop`, `place`, `throw`, `pulse`, `wait`, `reset`, `scan`) and
expected predicates. The headless harness replays the trace against a mock
world snapshot. A puzzle that cannot reach its win condition fails validation.

## Consequences

**Easier:**

- A level author can add a puzzle without touching TypeScript.
- Two different puzzle types can share one evaluator and one validator.
- The graph runs headless in unit tests and CI.
- Save/restore is a serialised graph state, not a set of closures.
- Evidence counters can describe how the player solved, not just whether they
  did.

**Harder:**

- The vocabulary is deliberately bounded. A designer who wants a new mechanic
  may need a new node type and a new ADR.
- The validator must know legal link pairs and win predicates.
- A graph is less immediately expressive than code; authors must think in
  nodes and edges.

**Constrained:**

- No per-puzzle scripts, callbacks, or embedded JavaScript.
- No arbitrary event-action rules. If the graph model cannot express a puzzle,
  the model is extended by ADR, not bypassed in content.
- The puzzle runtime stays free of engine and rendering imports.

## Alternatives considered

- **Puzzle as a room behaviour in TypeScript** — fastest for the ferry, but
  every new puzzle becomes code. Rejected; it does not prove a foundation.
- **Quiz gate plus a physics showcase** — preserves the existing gate engine
  but does not make the main path spatial. Rejected by the M1.5 brief.
- **Event-action rules (`on: { event, action, target }`)** — more expressive,
  but it is scripting under another name and makes validation weak.
- **Per-node state machines** — powerful, but a visual scripting language in
  data. Too large for M1.5.
- **Physics sensors for plates and zones** — couples the graph to Matter and
  makes headless tests depend on a physics world. Rejected; AABB checks over a
  snapshot are enough.
- **Three primitives only** — would make the second fixture a different
  configuration, not a different puzzle type. Rejected.
